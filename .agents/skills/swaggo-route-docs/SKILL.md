# Документация HTTP-маршрутов

Поддерживай соответствие фактического API, аннотаций Swaggo, сгенерированного OpenAPI и ReDoc в рамках текущей задачи. Применяй навык автоматически при работе Codex над созданием, изменением и удалением HTTP-маршрутов. Навык не является файловым наблюдателем и сам по себе не запускается после внешних изменений файлов.

## Определи контракт

Прочитай `backend/AGENTS.md`. Найди регистрацию затронутых маршрутов, обработчики, модели и middleware; учитывай вложенные роутеры и префиксы. Изучи существующие аннотации и директивы `go:generate` в `backend/cmd/server/main.go`.

Для каждого затронутого сочетания метода и пути установи фактические параметры, обязательность, форматы тела, успешные ответы, ошибки и авторизацию. Учитывай ответы middleware, cookies, заголовки, загрузку файлов и ответы без тела, когда они применимы. Не выдумывай коды статуса или схемы и не меняй поведение API ради удобства документации.

При просьбе документировать все существующие роуты проверь все зарегистрированные операции API, включая корневой health-маршрут. При обычном изменении ограничь правки затронутыми операциями и общими моделями, влияющими на них. Отличай операции API от монтирования вложенного роутера и инфраструктуры раздачи Swagger UI/контракта: монтирование само по себе не означает отдельную операцию API.

## Обнови исходные аннотации

Размещай аннотации рядом с функцией обработчика и следуй принятому в проекте языку и оформлению:

- Укажи `@Summary`, `@Tags` и `@Router` с фактическими методом и публичным путём. Для переменных пути используй `{name}`, учитывай базовый путь без дублирования префикса.
- Добавь `@Param` для применимых параметров и тела: расположение, тип, обязательность и существенные ограничения. Используй существующие модели и их JSON-теги.
- Укажи применимые `@Accept` и `@Produce`, реальные `@Success` и `@Failure` со схемами. Не назначай JSON ответам с текстом, файлами или без тела; учитывай фактическую оболочку ошибок.
- Добавляй `@Security` только при наличии соответствующей авторизации; проверь определение схемы безопасности и её имя. Публичные маршруты должны оставаться публичными в контракте.

При создании добавь полное описание новой операции. При изменении обнови описание контракта, включая операции, использующие изменённые общие модели. При смене метода или пути убери прежнюю операцию. При удалении убери соответствующие аннотации, сохранив описания других маршрутов того же обработчика и используемые ими модели.

Если обработчик находится в новом пакете, проверь, что каталог входит в область сканирования `swag init` в `go:generate`, и при необходимости обнови её.

## Синхронизируй OpenAPI, сгенерируй ReDoc и проверь

В этом проекте Swaggo создаёт Swagger 2.0, затем `backend/cmd/openapi` преобразует его в OpenAPI 3.0. После обновления аннотаций запусти [scripts/sync-docs.cmd](scripts/sync-docs.cmd). Скрипт сам переходит в `backend/`, выполняет `go generate ./cmd/server`, затем `generate-redoc.cmd` для создания `docs/redoc.html` из актуального `docs/openapi.json`. При ошибке прекращает цепочку и возвращает ненулевой код завершения.

Из корня репозитория:

```powershell
.\.codex\skills\swaggo-route-docs\scripts\sync-docs.cmd
```

Генерация ReDoc — обязательная часть синхронизации при создании, изменении и удалении маршрутов. После успешного завершения скрипта выполни проверки из `backend/`:

```powershell
go test ./...
go build ./cmd/server
```

Перед генерацией проверь, затрагивает ли изменение специальные преобразования в `cmd/openapi`: JSON/multipart профиля, cookies, BearerAuth и форматы ответов аватара. При изменении или удалении соответствующих операций обнови преобразователь и релевантные тесты; не оставляй обращения к удалённым путям. Прочитай актуальный код, прежде чем полагаться на этот список.

Включи обновлённые артефакты в `backend/docs/` в то же изменение. Не редактируй сгенерированные Swagger, OpenAPI, Go-файлы документации и ReDoc HTML вручную. При ошибке генерации устрани причину в аннотациях, моделях или преобразователе; не продолжай цепочку с устаревшим контрактом. Если необходимая команда недоступна, сообщи об ограничении и незавершённой генерации. При сбое ReDoc проверь причину в `generate-redoc.cmd` или его выводе; не считай синхронизацию документации завершённой, пока HTML не сгенерирован из актуального контракта.

Проверь `backend/docs/openapi.json` по затронутым операциям: наличие новых, актуальность изменённых, отсутствие удалённых; сверяй методы, пути, параметры, схемы, форматы, статусы и безопасность. Убедись, что ссылки на схемы разрешаются и общие модели согласованы. Успешная генерация сама по себе не доказывает полноту документации.

При изменении общего интерфейса выполни требования корневого `AGENTS.md` по согласованию с фронтендом и проверкам обеих частей. В результате кратко перечисли обновлённые операции, сгенерированные артефакты и фактические результаты проверок.
