# Ревью Uptime App

Ищи исправимые дефекты, внесённые изменениями, и объясняй их влияние на продукт. По умолчанию результат — отчёт на русском языке. Исправление кода и публикация замечаний в GitHub требуют соответствующего поручения; сама просьба о ревью их не разрешает. Для чтения diff не создавай и не переключай ветки, не меняй индекс и рабочие файлы.

## Выбор изменений

Прочитай корневой `AGENTS.md`, `docs/rules/git.md`, а для GitHub — `docs/rules/github.md`. Проверь `git status --short --branch`. Явно заданные пользователем границы имеют приоритет.

| Запрос | Что смотреть |
| --- | --- |
| Локальные изменения или ревью без уточнения | `git diff HEAD` — итоговые изменения отслеживаемых файлов; `git diff` и `git diff --cached` — при необходимости различить рабочее дерево и индекс. Новые файлы из status прочитай отдельно. |
| Только staged | `git diff --cached`; не включай unstaged и новые файлы вне индекса. |
| Конкретный коммит | `git show --format=fuller --find-renames <commit>`; для merge-коммита уточни нужного родителя, если от этого зависит объём ревью. |
| Ветка относительно базы | `git diff --find-renames <base>...<head>` и `git log <base>..<head>`; проверь итоговую разницу от merge-base, не только последний коммит. |
| PR | Узнай реальные base/head и описание PR через доступные средства GitHub, прочитай полный diff. Не примешивай локальные изменения. |

Для ветки без явно заданной базы используй `origin/main`, если ссылка существует, иначе локальный `main`. Сообщи выбранную базу и учитывай, что локальная ссылка может быть устаревшей. Не подменяй отсутствующую базу случайным коммитом. При неоднозначности задай один конкретный вопрос. Если локальных изменений нет, сообщи об этом, не переходи молча к ревью истории.

Сначала получи список файлов и статистику, затем прочитай весь diff порциями без пропуска обрезанного вывода. Учти добавления, удаления и переименования. Для новых файлов не выводи секреты из локальной конфигурации. Зафиксируй, какой снимок кода проверяешь: выводы о PR или коммите подтверждай по его head, а не по отличающемуся рабочему дереву.

## Чек-лист и архитектура

Всегда прочитай [references/checklist.md](references/checklist.md) и [references/architecture.md](references/architecture.md). Пройди каждый раздел чек-листа: для применимых пунктов собери доказательства, остальные отметь как неприменимые с краткой причиной на уровне раздела. Архитектурные правила проверяй и при изменении только одной части приложения. Отличай обязательные границы от описания текущего устройства и уже существующих компромиссов.

Запусти статические проверки из корня репозитория:

```powershell
node .codex/skills/code-review/scripts/static-checks.mjs
```

По умолчанию проверяются итоговые локальные изменения и untracked-файлы. Для индекса передай `--staged`; для ветки или PR — `--base <base> --head <head>`. Скрипт читает выбранный снимок без checkout и проверяет whitespace/conflict markers, JSON, формат Go и новые запрещённые импорты фронтенда. Для анализа импортов использует установленный в `frontend/` TypeScript. Зависимости не устанавливает, файлы не изменяет, тесты и сборки не запускает.

Вывод — JSON с результатами, путями и строками, без содержимого исходников. Коды выхода: `0` — применимые проверки прошли, `1` — есть нарушения, `2` — ошибка запуска или неполная проверка (например, отсутствует gofmt/TypeScript). При отсутствии изменений явно сообщает об этом. Для отдельного коммита используй `--base <parent> --head <commit>` только если его merge-base с родителем соответствует нужному сравнению; для корневого коммита и сложных merge-сравнений проверь diff вручную и сообщи ограничение скрипта.

Результаты скрипта — входные данные для ревью: подтверди связь с diff и влияние перед включением в замечания. Он не проверяет API, авторизацию и всю архитектуру. В итоговом отчёте добавь компактную таблицу разделов чек-листа со статусами «проверено», «есть замечания», «неприменимо», «не проверено» и причиной для последних двух; не называй непройденный пункт проверенным.

При изменении скрипта запусти `node --test .codex/skills/code-review/scripts/static-checks.test.mjs`. Тесты используют временные Git-репозитории; для полного набора нужны установленный TypeScript фронтенда и gofmt.

## Контекст изменений

Прочитай `AGENTS.md` затронутых каталогов, включая вложенные инструкции. Не ограничивайся изменёнными строками: проследи вызовы, данные, обработку ошибок и затронутые тесты. Проверяй другую часть приложения, если изменение может повлиять на её поведение, даже когда её файлов нет в diff. Устаревшие описания структуры в инструкциях сверяй с фактическим кодом.

## Подтверждение выводов

Для каждого кандидата установи: что изменилось относительно базы, при каком входе или состоянии проявляется ошибка, каков наблюдаемый результат и почему существующий код её не предотвращает. Найди все существенные вызовы и проверки перед выводом о сломанном контракте. Отделяй намеренное изменение поведения от регрессии.

Используй проверки из актуальных `AGENTS.md` для затронутых частей. Сейчас базовые команды:

- Из `backend/`: `go test ./...`, `go build ./cmd/server`.
- Из `frontend/`: `npm test`, `npm run typecheck`, `npm run build`; для затронутых браузерных сценариев — релевантные тесты `npm run test:e2e`.
- При изменении общего API проверь обе части. Для скрипта запуска смотри проверку в корневом `README.md`.

Сначала проверь предпосылки и побочные эффекты команд. Если выбранный снимок отличается от рабочего дерева, не выдавай проверки рабочего дерева за проверку этого снимка: используй изолированную копию или явно укажи ограничение. Интеграционные тесты с `TEST_DATABASE_URL` требуют тестовой БД; не направляй их в рабочую базу. Отметь пропуски внутри успешно завершившегося набора тестов. Не устанавливай инструменты, не запускай миграции и не меняй исходники ради подтверждения без необходимости и соответствующих разрешений. Ошибка окружения не доказывает дефект diff.

Включай в замечания только подтверждённые дефекты и конкретные нарушения правил проекта. Не выдавай вкусовые предложения, абстрактные риски, старые ошибки или отсутствие теста само по себе за дефект. Если доказательств не хватает, вынеси конкретный открытый вопрос отдельно. Не создавай искусственную квоту замечаний и не дублируй одну причину в нескольких местах.

## Результат

Кратко укажи проверенный диапазон или состав локальных изменений. Затем перечисли замечания по убыванию важности:

- **P0** — блокирующая проблема с катастрофическими последствиями, не зависящая от редких условий.
- **P1** — серьёзная ошибка: утечка данных, нарушение изоляции пользователей, потеря данных или поломка основного сценария.
- **P2** — значимый дефект при конкретных условиях, который следует исправить.
- **P3** — небольшой подтверждённый дефект с ограниченным влиянием.

Для каждого замечания используй заголовок `[P1] Краткое описание`, ссылку на файл и минимальный диапазон строк, сценарий воспроизведения и последствие. Привязывай замечание к изменённым строкам; для удалённого кода укажи место в старой версии. Объяснение должно позволять исправить причину без догадок. Предложи направление исправления, если оно не очевидно, без переписывания всего участка.

После замечаний укажи выполненные проверки и их результаты, затем существенные ограничения или открытые вопросы. Если дефектов не найдено, напиши «Замечаний не найдено» и сообщи пределы проверки; успешные тесты сами по себе не гарантируют отсутствие ошибок. Не публикуй отчёт в PR без поручения пользователя.
