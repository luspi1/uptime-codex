# Архитектурные признаки Uptime App

Это карта текущего проекта и критерии ревью, а не требование провести рефакторинг. Сверяй её с AGENTS и кодом проверяемого снимка. При намеренном изменении архитектуры проверяй новый контракт и обновление этой карты; не требуй сохранения конкретного файла ради самого пути.

## A1. Направление зависимостей frontend

Источник: `frontend/AGENTS.md`.

- `app/` отвечает за маршруты, layout, metadata и композицию страниц.
- `features/<feature>/` содержит формы, клиентское состояние, предметную логику и связанные типы/API.
- `components/<Component>/` содержит общие UI-компоненты, управляемые через props, без зависимости от `features/` и `app/`.
- `features/` не импортирует `app/`. Между features зависимости допустимы: dashboard/profile уже используют auth.
- Между областями используется `@/`; внутри компонента/области — относительные пути. CSS-модули и ресурсы компонента располагаются рядом с ним.

Автоматически проверяются новые импорты `components → features/app` и `features → app`: обычные import, export from, import type, import(), require() и import = require() с литеральным путём, включая относительные пути. Остальное проверяется вручную. Скрипт понимает текущий `@/` и относительные пути; новые aliases, вычисляемые импорты и транзитивные обходы требуют ручной проверки.

## A2. Сессия и транспорт frontend

Текущие опорные файлы: `features/auth/api.ts`, `features/auth/components/AuthProvider/AuthProvider.tsx`, `app/layout.tsx`.

Общий транспорт, проверка ответов, access-токен в памяти, единый refreshPromise и ограниченный повтор после 401 сосредоточены в API-клиенте. AuthProvider разделяет пользователя и состояние сессии между маршрутами; страницы используют общий провайдер. Refresh хранится в HttpOnly cookie. Проверяй, что новая feature не создаёт параллельную ротацию refresh, отдельное хранилище токенов или рассинхронизированную копию профиля.

Существующий компромисс: типы и вызовы monitors пока тоже находятся в `features/auth/api.ts`. Это не новый дефект и не запрет на их обоснованное выделение. При выделении сохраняется единая семантика авторизованных запросов.

## A3. Граница server/client

`app/layout.tsx` и страницы собирают интерфейс; интерактивные feature-компоненты используют `"use client"`. Общие UI-компоненты могут быть клиентскими, если им нужны hooks. Проверяй, что browser API не попали в серверный путь исполнения, а серверные зависимости и секреты — в клиентский bundle. API и соглашения Next.js сверяй с локальными docs установленного пакета.

## A4. Сборка backend и обработчики

`backend/cmd/server/main.go` загружает конфигурацию, подключает PostgreSQL, запускает миграцию, собирает HTTP mux и сервер. Реализация HTTP-сценариев находится в `internal/`, не в точке входа.

Текущая цепочка: `cmd/server → auth.NewHandler → monitors.NewHandler`. Auth Handler применяет общую Origin/CORS политику и передаёт monitors callback аутентификации. Пакет monitors не импортирует auth; зависимость передаётся через `Authenticate`. При изменении сборки проверяй, что маршруты не обходят общие проверки и не возникает обратная зависимость/cycle. Go запрещает import cycle, но отсутствие цикла само по себе не доказывает сохранение middleware.

В проекте используются `net/http` и прямые вызовы GORM из обработчиков. Отдельных обязательных service/repository слоёв нет; не требуй их внедрения в обычном ревью.

## A5. Данные и владение

`auth/model.go` содержит User/RefreshSession и общий `Migrate`, включающий monitors.Monitor. Monitors хранит UserID, получает его из аутентификации и ограничивает выборки владельцем. Браузер не является источником доверенного UserID. Проверяй сохранение этой границы во всех новых операциях и совместимость AutoMigrate с существующими данными.

Связь `auth → monitors` в миграции и сборке — текущее устройство; сама по себе она не повод требовать переписывание. Миграции и интеграционные тесты меняют схему переданной БД.

## A6. Контракт HTTP

Backend — источник серверного поведения и валидации; frontend учитывает тот же контракт, но его валидация не заменяет серверную. Ошибки имеют `error.code`/`error.message`, access JWT передаётся как Bearer, refresh — cookie. Для конкретных операций смотри актуальные обработчики, `README.md` и `docs/monitoring-points.md`.

Аннотации Swaggo → Swagger 2 → `cmd/openapi` → OpenAPI 3 → ReDoc. Контракты и HTML генерируются; ручное исправление только производного файла не исправляет источник. Ревью проверяет согласованность всей затронутой цепочки без регенерации в рабочем дереве.

## A7. Состояние продукта и файлы

Точки мониторинга пока сохраняются и перечисляются; опрос и история доступности не следуют автоматически из названия продукта. Подтверждай объём новой функции по задаче и diff.

Аватары хранятся вне БД в каталоге uploads/AVATAR_DIR, ссылка — в профиле. При изменениях проверь жизненный цикл файла вместе с транзакцией БД и публичной выдачей. `.env`, локальные uploads и результаты сборки не являются исходниками для коммита; примеры настроек — `.env.example`.

## A8. Проверяемость и границы автоматизации

Go-тесты расположены рядом с пакетами, клиентские API-тесты — в `frontend/test/`, браузерные проверки используют Playwright и могут подменять HTTP. Мок API подтверждает поведение UI, но не совместимость с реальным backend. Проверки запуска описаны в корневом README и AGENTS частей.

Статический скрипт проверяет только изменённые файлы выбранного снимка. JSON/gofmt проверяют файл целиком; архитектурные ошибки фильтруются относительно базы, чтобы не выдавать неизменённые запрещённые зависимости за новые. Он не выполняет typecheck, go vet, тесты и сборки, не проверяет транзитивный граф импортов и не обнаруживает ошибки бизнес-логики. Эти проверки выполняются отдельно по AGENTS и diff.
