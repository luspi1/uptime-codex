# Создание точек мониторинга

На главной странице пользователь открывает форму кнопкой «Добавить сайт», вводит URL и частоту опроса в минутах, затем нажимает «Создать». После успешного ответа форма закрывается, а точка появляется в списке. При ошибке введённые значения сохраняются для повторной попытки. Во время запроса повторная отправка и закрытие формы заблокированы.

Точки хранятся в таблице `monitors`, создаваемой через GORM AutoMigrate при запуске backend. Каждая запись привязана к пользователю из access JWT. Список содержит только его точки, начиная с последней созданной. Опрос сайтов, история проверок и вычисление статуса доступности в эту задачу не входят; интерфейс показывает «Ещё не проверялся».

## Контракт API

Оба метода требуют `Authorization: Bearer <JWT>` и используют существующие правила CORS. Клиент обновляет истёкший JWT через `/api/auth/refresh` и повторяет запрос один раз.

- `GET /api/monitors` → `200`, массив точек; пустой список возвращается как `[]`.
- `POST /api/monitors` принимает JSON `{"url":"https://example.com/health","interval_minutes":5}` → `201`, созданная точка.

Формат точки:

```json
{
  "id": 1,
  "url": "https://example.com/health",
  "interval_minutes": 5,
  "created_at": "2026-10-26T12:00:00Z"
}
```

URL должен содержать схему `http` или `https` и хост, не содержать логин, пароль или фрагмент `#`; длина после удаления пробелов по краям — не более 2048 байт. Частота опроса — целое число от 1 до 1440 минут, по умолчанию в форме 5. Неизвестные JSON-поля и дополнительные JSON-объекты отклоняются. Сервер не обращается к указанному URL при создании.

Ошибки имеют формат `{"error":{"code":"invalid_request","message":"..."}}`: некорректный запрос — `400 invalid_request`, отсутствие или недействительность JWT — `401 invalid_token`, недопустимый Origin — `403 origin_not_allowed`, сбой БД — `500 internal_error`.

## Проверки

Из `backend/`: `go test ./...`, `go build ./cmd/server`. Для интеграционных тестов задайте `TEST_DATABASE_URL` на PostgreSQL: тесты выполняют миграцию схемы, а тестовые записи откатывают транзакцией. Проверяются создание через HTTP-обработчик, сохранённые поля в БД, загрузка списка владельцем, изоляция пользователей, отказ без JWT и валидация без записи в БД.

Из `frontend/`: `npm test`, `npm run typecheck`, `npm run build`, `npm run test:e2e`. Браузерные тесты подменяют API и проверяют форму на обычном и мобильном экранах: валидацию, повтор после ошибки, блокировку повторной отправки, отмену, появление точки и загрузку списка после перезагрузки, а также повтор загрузки после сетевой ошибки.

Если Next.js уже запущен, задайте `PLAYWRIGHT_BASE_URL=http://localhost:3000`, чтобы тесты использовали существующий сервер. При необходимости путь к установленному Chrome задаётся через `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. В PowerShell с запретом выполнения `.ps1` используйте `npm.cmd`.

Снимки интерфейса создаются браузерными тестами в `frontend/test-results/monitor-form-desktop.png`, `monitor-form-mobile.png`, `monitor-created-desktop.png` и `monitor-created-mobile.png` и могут быть приложены к PR.
