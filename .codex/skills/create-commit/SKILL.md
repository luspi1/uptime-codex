# Создание коммита

## Границы задачи

Учитывай инструкции текущего проекта, если они есть: правила Git, соглашения о сообщениях и необходимые проверки. Skill самодостаточен и не требует определённой структуры репозитория. Явные указания пользователя и правила проекта имеют приоритет над рекомендациями по умолчанию ниже.

Явная просьба пользователя создать коммит в определённых рамках уже является согласованием; не запрашивай его повторно. Если пользователь просит только подготовить сообщение, верни текст без изменения индекса и истории. Не выполняй push, создание PR или переписывание истории без соответствующего поручения.

## Подготовка содержимого

1. Проверь `git status --short --branch`, `git diff` и `git diff --cached`. Отдельно изучи новые файлы: обычный diff их не показывает. Определи изменения, относящиеся к задаче, включая уже добавленные в индекс.
2. Один логический шаг — один коммит. Код, его тесты и необходимую документацию сохраняй вместе. Независимые изменения разделяй. Не включай посторонние правки пользователя, секреты и локальную конфигурацию.
3. Выполни проверки, принятые в проекте и соразмерные изменениям. При изменении общего интерфейса проверь затронутых потребителей. Используй уже полученные результаты, если проверенный код не менялся. Не выдавай пропущенные или упавшие проверки за успешные; сообщи о них до коммита и устрани относящиеся к задаче ошибки, когда это возможно.
4. Добавляй только выбранные пути через `git add -- <paths>`, а при смешанных правках в одном файле — выбранные фрагменты. Избегай `git add .`, `git add -A` и `git commit -a`: они могут захватить чужие изменения. Если в индексе уже есть посторонние правки, не сбрасывай их и не включай в коммит; согласуй состав с пользователем, если безопасно отделить изменения не получается.
5. Перед созданием коммита проверь `git diff --cached --check`, `git diff --cached --stat` и полный `git diff --cached`. Сообщение должно описывать именно этот diff. При пустом индексе сообщи, что коммитить нечего; пустой коммит без отдельной просьбы не создавай.

## Сообщение по Conventional Commits

```text
<type>[(scope)][!]: <description>

[body]

[footers]
```

Скобки `[]` обозначают необязательные части и не входят в сообщение. Двоеточие и пробел после него обязательны.

Базовые типы:

| Тип | Назначение |
| --- | --- |
| `feat` | Новая возможность приложения |
| `fix` | Исправление ошибки |
| `refactor` | Изменение структуры кода без новой возможности или исправления ошибки |
| `test` | Добавление или изменение тестов |
| `docs` | Изменение документации |
| `chore` | Обслуживание проекта, инструменты и зависимости |

Если это принято в проекте, используй дополнительные типы, например `build`, `ci`, `perf`, `style`. Conventional Commits не ограничивает список типов этими примерами.

- Выбирай тип по результату изменения, а не по расширению файлов. Например, тест регрессии вместе с исправлением относится к `fix`.
- Необязательный `scope` уточняет область изменения, например `parser` или `cli`. Выбирай его по структуре текущего проекта и опускай, если он не помогает понять изменение.
- По умолчанию заголовок пиши на английском языке, в повелительном наклонении, без точки в конце. Весь заголовок, включая тип и scope, — до 72 символов. Это рекомендации по оформлению, а не требования самой спецификации; следуй другому формату, если он задан пользователем или проектом.
- Без эмодзи, общих фраз вроде `update stuff`, `significantly improved` и неподтверждённых утверждений.
- Тело добавляй только для объяснения причины, ограничений или важного компромисса, которые не очевидны из diff. Отделяй его пустой строкой; не пересказывай список изменённых файлов.
- Несовместимое изменение публичного контракта обозначай `!` перед двоеточием или footer `BREAKING CHANGE: <description>`. Можно использовать оба: маркер делает изменение заметным, footer объясняет несовместимость и переход. Само наличие изменений API ещё не означает нарушения совместимости.
- Footers отделяй пустой строкой. Добавляй ссылки на задачи только при известных номерах; `Refs: #123` — ссылка, `Closes: #123` — только если задача действительно решена и её закрытие входит в поручение. Не выдумывай авторство и подписи.

Примеры заголовков:

```text
feat(cli): add JSON output
fix(parser): handle empty input
docs: explain local setup
```

Пример сообщения с несовместимым изменением:

```text
feat(config)!: require an explicit timeout

Implicit defaults hide configuration errors.

BREAKING CHANGE: the timeout setting is now required.
Add timeout to existing configuration files before upgrading.
```

## Создание и проверка

Создавай коммит только в рамках поручения пользователя. Если правила проекта требуют дополнительного согласования или определённой ветки, соблюдай их; перед запросом согласования подготовь и проверь изменения, покажи состав и точное сообщение. Не создавай и не переключай ветку только ради выполнения skill, если этого не требуют задача или правила проекта. При detached HEAD уточни целевую ветку до коммита.

Для простого заголовка используй `git commit -m '<message>'` с корректным экранированием оболочки. Для многострочного сообщения сохрани точный текст в UTF-8 во временный файл вне отслеживаемых файлов и используй `git commit -F <file>`; не помещай текст сообщения в исполняемый код оболочки.

Не обходи hooks через `--no-verify` и не применяй `--amend` без явного поручения. При ошибке остановись, выясни причину и проверь `git status` и последний коммит перед повтором: hooks могли изменить файлы. Исправление hooks или новые staged-изменения требуют повторной проверки diff и релевантных проверок.

После успеха проверь `git log -1 --format=fuller`, `git show --stat --oneline HEAD` и `git status --short --branch`. Сообщи короткий хеш, заголовок, результаты проверок и оставшиеся незакоммиченные изменения, если они есть.
