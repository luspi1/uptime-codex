# Сводка за предыдущий день работы

Подготовь короткий текст на русском языке, который можно сразу озвучить на совещании: что сделали и какой результат получили. Источник — локальная история Git текущего репозитория; не изменяй файлы, индекс или ветку ради отчёта.

## Период и источники

- Если пользователь указал дату, период, ветку или автора, используй эти ограничения. Иначе рассматривай все коммиты, достижимые из `HEAD`, без фильтра по автору и без `--all`.
- По умолчанию предыдущий день работы — самая поздняя календарная дата строго раньше сегодня, за которую есть коммиты в выбранной истории. Пропускай дни без коммитов, включая выходные; не подменяй этот период последними 24 часами. Если явно просят «за вчера», используй вчерашнюю календарную дату и не переходи к более ранней при отсутствии изменений.
- Используй часовой пояс пользователя из контекста, иначе локальный часовой пояс среды. Сопоставляй даты по времени коммиттера, приведённому к этому поясу, а не по дате автора или исходному смещению коммита.
- Получи текущую ветку и состояние через `git status --short --branch`. Для выбора даты и коммитов используй `git log --format='%H%x09%cI%x09%s'`; сначала преобразуй временные метки в выбранный часовой пояс, затем фильтруй по календарной дате. Не полагайся на порядок вывода как на сортировку по времени: даты в истории могут идти не по порядку.
- Если подходящих коммитов нет, сообщи об этом. Не делай вывод, что над проектом не работали: Git не отражает всю работу. Незакоммиченные изменения нельзя достоверно отнести к выбранному дню; не включай их в его результаты.

## Анализ изменений

Прочитай сообщения и статистику выбранных коммитов (`git show --stat <hash>`), затем изучи относящиеся к задачам изменения через `git show <hash>`. Опирайся на diff, а не только на заголовки. Для больших изменений читай затронутые файлы выборочно, отмечая существенные ограничения анализа.

Объединяй связанные коммиты в результаты работы: фронтенд, бэкенд, API, документация и инструменты — только если они действительно менялись. Учитывай исправления и отмены внутри выбранного дня, чтобы не выдавать отменённую возможность за готовую.

Не дублируй результаты merge-коммита и вошедших в него коммитов. При необходимости изучи родителей merge и отдельно учти изменения, появившиеся при разрешении конфликтов. Не утверждай, что изменение выпущено или развёрнуто, лишь потому что оно есть в Git.

Упоминай проверки только при наличии подтверждения в доступных источниках; наличие тестов в diff не доказывает их успешный запуск. Не запускай тесты только ради исторического отчёта: их текущий результат не подтверждает результат выбранного дня.

## Ответ

Дай готовый устный рассказ, обычно один короткий абзац на 20–40 секунд. Для нескольких независимых задач допустимы короткие пункты, которые удобно прочитать вслух. Обозначь дату простыми словами, например «За 29 октября…»; слово «вчера» используй только для вчерашней календарной даты.

Начинай с выполненной работы: «Добавили…», «Исправили…», «Подготовили…». Для каждого результата поясни, что теперь можно сделать или что стало удобнее. Объединяй технические шаги одной задачи в одну понятную мысль. Не преувеличивай пользу, если она не следует из изменений.

Не перечисляй файлы, команды, библиотеки, хеши коммитов, ветку и часовой пояс. Технические названия оставляй, только если без них теряется смысл для слушателя. Вместо «настроили генерацию OpenAPI из аннотаций Swaggo» скажи «добавили автоматическое обновление документации при изменении API». Ссылки на коммиты и технические подробности приводи только по запросу; при подготовке рассказа сохраняй связь каждого утверждения с изученными изменениями.

Пример подачи, если это подтверждено историей:

> За 29 октября добавили документацию API: теперь разработчики могут посмотреть доступные запросы, форматы данных и ошибки, а также попробовать запросы прямо в браузере. Подготовили отдельную версию документации, которую можно открыть без запуска сервера, и автоматизировали её обновление.

Если пользователь явно просит личный отчёт, учитывай его авторство; при неизвестной личности уточни автора, продолжая собирать общую сводку. По умолчанию описывай изменения проекта без приписывания всей работы пользователю.

Блокеры, незавершённую работу и планы добавляй только при наличии фактов или указаний пользователя. Не придумывай раздел «сегодня» по вчерашним коммитам. Не добавляй служебные оговорки вроде «подтверждения запуска тестов нет», если не заявляешь об успешных проверках. Существенную неполноту анализа, которая мешает достоверно описать результат, обозначь отдельной короткой заметкой после текста для совещания.
